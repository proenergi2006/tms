# TMS — Dokumentasi Proyek

Transport Management System (TMS) — pengganti sistem operasional logistik berbasis Google Apps Script, dibangun dengan Laravel 12 + Vue 3 (Materio/Vuetify) + MySQL, terintegrasi dengan SYOP native.

## Daftar Dokumen

0. [BRD (Business Requirements Document) v1.1](00-BRD.md) — business case, proses as-is/to-be, RACI, business rules, kerangka budget, metrik keberhasilan, dan lembar persetujuan. Melengkapi PRD dengan elemen level bisnis; bagian bertanda [DIISI TIM BISNIS] masih menunggu data dari pemilik proses. v1.1 memperbarui struktur peran & approval sesuai hasil implementasi final (SA, Fleet Operations → Kepala Pool, Logistik HO).
1. [PRD (Product Requirements Document) v1.1](01-PRD.md) — latar belakang, tujuan, ruang lingkup, keputusan arsitektur tingkat tinggi.
2. [Architecture Document v1.0](02-Architecture.md) — arsitektur frontend, backend, data, integrasi, keamanan, deployment.
3. [Design Document v1.0](03-Design-Document.md) — desain skema DB (ringkasan), spesifikasi API, alur proses/state machine, desain UI.
4. [Wireframe Document](04-Wireframe.md) — wireframe low-fidelity untuk Web Admin & aplikasi lapangan.
5. [DB Schema (DDL)](05-DB-Schema.sql) — skema lengkap `tms_db` dalam SQL MySQL, siap dipetakan ke migration Laravel.
6. [Panduan Pengguna](06-Panduan-Pengguna.md) — tata cara memakai aplikasi per peran, mulai dari login sampai alur kerja harian.

## Status

PRD (Bagian 4–7, 12, 14, 15), Architecture Document (ringkasan tech stack, matriks integrasi), dan Design Document (daftar endpoint API) sudah lengkap. Diagram (context diagram, ERD, component diagram, deployment, flow, state machine, sinkronisasi SYOP) disediakan sebagai diagram Mermaid langsung di dalam dokumen — dapat dirender ulang menjadi gambar formal bila diperlukan untuk presentasi.

Backend (`../backend/`) sudah mengimplementasikan seluruh endpoint pada Design Document Bagian 3.2–3.6 (81 route, teruji end-to-end lewat smoke test manual: pengajuan → auto-create Work Order → rantai approval Kepala Pool/BM/Tim Logistik/Finance data-driven via `approval_rules` → finalisasi otomatis `maintenance_history` + `operational_cost` → laporan profitabilitas). Lihat catatan implementasi Bagian 3.3 Design Document untuk keputusan desain Request ↔ Work Order.

Frontend (`../frontend/`) sudah mengimplementasikan seluruh halaman Wireframe Document Bagian 2 (Dashboard, Daftar Pengajuan, Detail Work Order/SPK, Antrian Approval, Detail Armada 5-tab, Asset Registry, Laporan Profitabilitas Armada) dan Bagian 3 (aplikasi lapangan: Buat Pengajuan, Pengajuan Saya, Update Status SPK, dengan `FieldLayout` terpisah dari panel admin sesuai PRD 8.5). Ditambah satu halaman Master Data (referensi driver/mekanik/vendor/dll, di luar penomoran wireframe asli) karena sidebar admin membutuhkan tujuan navigasi untuk menu tersebut. Diuji end-to-end di browser sungguhan (headless Chromium): login → buat pengajuan → approve berjenjang lintas role → pindah ke riwayat, tanpa error console/network.

RBAC per-endpoint (Architecture Document Bagian 7.2) sudah diimplementasikan: tabel `permissions`/`role_permissions` (sudah ada di DB Schema sejak awal, sebelumnya belum dipakai) diisi lewat `RolePermissionSeeder` — 14 permission granular per modul (mis. `request.create`, `approval.act`, `fleet.manage`, `asset.view`) dipetakan ke 9 role sesuai PRD Bagian 4 & akses role pada Wireframe Bagian 2. Setiap route digembok `->middleware('permission:<nama>')` (lihat `App\Http\Middleware\EnsurePermission`), diverifikasi lewat 11 skenario allow/deny lintas modul via curl. Frontend menyaring menu sidebar dan tombol aksi sesuai permission pengguna (`auth.hasPermission()`), dan Dashboard hanya mengambil data yang relevan untuk role tersebut — namun ini murni gating tampilan; backend tetap satu-satunya sumber otorisasi.

Notifikasi otomatis (FR-11, FR-17) sudah diimplementasikan lewat `App\Services\NotificationService`, dipakai dua pola berbeda sesuai Architecture Document Bagian 4.5:
- **FR-11 (event-driven)** — `ApprovalWorkflowService::notifyCurrentStage()` mengirim notifikasi ke seluruh user dari role approver tahap berikutnya (diutamakan yang satu cabang dengan armada terkait, fallback ke seluruh role bila cabang tidak match), dipicu saat Work Order dibuat (`RequestController::store()`) maupun setiap kali approve() bergerak ke tahap baru. Requester juga dinotifikasi saat pengajuannya ditolak atau selesai.
- **FR-17 (terjadwal)** — command `notifications:check-legal-expiry` (dijadwalkan harian jam 07:00 lewat `routes/console.php`) memindai `fleet_legal_docs` yang mendekati jatuh tempo (default 30 hari) dan mengirim ke Tim Logistik cabang terkait, dengan dedup 7 hari per dokumen (`NotificationService::notifyRoleOncePerWindow()`) agar tidak membanjiri notifikasi selama masa mendekati jatuh tempo.
- Ikon lonceng di topbar (`NotificationMenu.vue`) sudah tersambung di kedua layout (admin & aplikasi lapangan), dengan badge unread dan polling 60 detik. Diuji end-to-end di browser sungguhan: pengajuan → notifikasi ke Kepala Pool → approve → notifikasi ke BM → reject → notifikasi ke requester; serta command legal-expiry → notifikasi ke Tim Logistik.

Ekspor laporan profitabilitas kini `.xlsx` asli (bukan CSV lagi) via `maatwebsite/excel` (`App\Modules\Fleet\Exports\FleetProfitabilityExport`). Dua bug ditemukan & diperbaiki selagi mengerjakan ini:
- `window.open()`/anchor biasa ke endpoint export tidak menyertakan header `Authorization` (token disimpan di memory, bukan cookie) — akan selalu 401. Diperbaiki: frontend mengambil file lewat axios (`responseType: 'blob'`, ikut interceptor auth) lalu memicu unduhan lewat anchor sementara (`utils/download.js`).
- `PhpSpreadsheet\Worksheet::fromArray()` (dipakai concern `FromArray`) membandingkan nilai sel dengan `$nullValue` memakai `==` (longgar) — nilai `0`/`0.0` (biaya/profit yang benar nol) ikut cocok dengan `null` dan selnya jadi kosong, bukan `0`. Diperbaiki dengan menulis sel secara manual lewat event `AfterSheet` + `setCellValueExplicit()` (tipe eksplisit), bukan lewat `fromArray()`. Diverifikasi: file hasil ekspor dibuka ulang lewat PhpSpreadsheet dan lewat unduhan browser sungguhan (Playwright), nilai nol maupun nilai riil (mis. Rp 550.000) tampil benar dengan pemisah ribuan.

Halaman **Aturan Approval** (`/approval-rules`, permission `approval-rule.manage` — khusus Admin Sistem) sudah dibuat untuk mengelola `approval_rules` (FR-09) lewat UI, bukan cuma API — di luar penomoran Wireframe asli, sama seperti halaman Master Data. Role pada form dikunci ke "Finance" karena `ApprovalWorkflowService` memang hanya pernah membaca aturan dengan `role="finance"` (tiga tahap pertama tetap baku di skema, bukan konfigurasi), jadi UI tidak menawarkan opsi yang sebenarnya tidak berpengaruh. Diuji end-to-end: menu tersembunyi bagi role tanpa permission ini, tambah/ubah aturan tersimpan dan konsisten dengan API.

Halaman **Notifikasi** (`/notifications`, tanpa gate permission khusus — hanya menampilkan milik user yang login) dan **Audit Log** (`/audit-logs`, permission `audit-log.view` — khusus Admin Sistem) sudah dibuat:
- Notifikasi: daftar penuh (bell di topbar hanya 20 terbaru), tab Semua/Belum Dibaca/Sudah Dibaca, tombol "Tandai Semua Dibaca" (`PATCH /notifications/read-all`, endpoint baru). Ada di kedua layout (admin & aplikasi lapangan) lewat link "Lihat Semua" pada dropdown bell.
- Audit Log: endpoint baru `GET /audit-logs` (read-only, permission baru `audit-log.view`) menampilkan `App\Models\AuditLog` yang sudah ditulis `ApprovalWorkflowService::log()` sejak awal tapi belum ada UI/API untuk membacanya. Filter entity/aksi/tanggal, kolom "Perubahan" meringkas `before_data`/`after_data` jadi `field: sebelum → sesudah` per field yang benar berubah.
- Diuji end-to-end dengan data nyata hasil satu siklus approval penuh: 4 baris audit log (Kepala Pool → BM → Tim Logistik → Finance) tampil dengan diff `approval_status` yang benar; menu Audit Log terbukti tersembunyi bagi role tanpa permission.
- Keterbatasan kecil yang diketahui (bukan bug fungsional): badge unread di bell topbar tidak langsung ter-refresh setelah "Tandai Semua Dibaca" dari halaman `/notifications` terpisah — baru sinkron pada polling 60 detik berikutnya, karena kedua komponen tidak berbagi state secara reaktif.

Halaman **Master Data** (`/master-data`, permission `master-data.manage` untuk tambah/ubah/hapus — hanya Tim Logistik & Admin Sistem) kini CRUD penuh, bukan lagi read-only: 8 entitas (Cabang, Driver, Mekanik, Vendor/Bengkel, Gudang, Sparepart, Jenis Biaya, Jenis Pekerjaan) memakai satu komponen `MasterDataHub.vue` berbasis field-spec dinamis per tab (`{key,label,type,required,options|optionsSource,editOnly}`) agar tidak perlu 8 komponen CRUD yang hampir identik. Tab Cabang ditambahkan (sebelumnya belum ada UI sama sekali untuk `branches`, padahal API-nya sudah ada). Halaman **Armada** juga menyusul: `FleetsList.vue` sekarang punya tombol "+ Tambah Armada", dan `FleetDetail.vue` punya tombol "Ubah Armada" di header — keduanya digembok `master-data.manage` (bukan `fleet.manage`, yang khusus dipakai endpoint riwayat/legalitas/fuel-log di `routes/modules/fleet.php`). Diuji end-to-end di browser sungguhan (Playwright): create/edit/delete Cabang round-trip benar ke DB, create fleet baru + edit plate number pada Detail Armada round-trip benar, dan tombol "Tambah"/"Tambah Armada" terbukti tersembunyi bagi role tanpa `master-data.manage` (dites dengan role Manajemen, yang hanya punya `master-data.view`). Satu detail yang perlu diingat: enum `fleets.status` di DB adalah `aktif`/`maintenance`/`nonaktif` (bukan `perbaikan`) — dialog ubah armada memakai daftar ini persis.

Audit lanjutan ("halaman apa lagi yang masih kurang") menemukan dan menutup dua gap kecil:
- **Lampiran Work Order** — `WorkOrderDetail.vue` sebelumnya tidak punya UI sama sekali untuk melihat/mengunggah lampiran, padahal endpoint `POST /work-orders/{workOrder}/attachments` sudah ada sejak awal dan foto yang diunggah user lewat form pengajuan lapangan (`FieldNewRequest.vue`) tidak pernah terlihat lagi oleh siapa pun. Ditambahkan kartu "Lampiran" dengan dua daftar (dari pengajuan — read-only; dari pelaksanaan — bisa unggah baru, digembok `work-order.manage`) plus eager-load `request.attachments` yang sebelumnya belum dimuat di `WorkOrderController::show()`. File disimpan di disk publik (`Storage::disk('public')`) sehingga tautan unduh bisa langsung `href`/`target=_blank` tanpa perlu pola blob-fetch (beda dari ekspor `.xlsx` yang butuh header Authorization).
- **Hapus Aset** — `AssetsList.vue` sudah punya create/edit tapi tombol hapus belum ada, padahal `assetsApi.remove()` dan endpoint `assets.destroy` sudah lengkap. Ditambahkan tombol hapus per baris + `ConfirmDialog`, digembok `asset.manage`.

Keduanya diuji end-to-end di browser sungguhan (Playwright): pengajuan dengan foto lampiran → Work Order otomatis menampilkan lampiran tsb → unggah lampiran tambahan dari WorkOrderDetail → dua lampiran tampil; aset baru dibuat → dihapus → baris hilang dari tabel.

**Bug logout ditemukan & diperbaiki**: tombol "Nama Pengguna ▾" di pojok kanan atas (`DefaultLayout.vue`) ternyata cuma `v-btn` polos tanpa `v-menu`/handler apa pun — terlihat seperti dropdown tapi tidak melakukan apa-apa saat diklik, dan `FieldLayout.vue` (aplikasi lapangan) malah tidak punya elemen logout sama sekali, padahal `auth.logout()` di Pinia store sudah ada sejak awal (dipakai internal oleh interceptor 401 axios) tapi tidak pernah dipanggil dari UI. Diperbaiki: `DefaultLayout.vue` sekarang punya `v-menu` beneran dengan item "Keluar", `FieldLayout.vue` dapat ikon logout di top bar. Diuji end-to-end (Playwright): klik dropdown → klik Keluar → token Pinia bersih → redirect ke `/login`.

**RBAC per-cabang (multi-branch scoping) sudah diimplementasikan** — PT Pro Energi punya 7 cabang operasional riil (Jakarta, Surabaya, Samarinda, Sulawesi, Palembang, Pontianak, Banjarmasin), masing-masing dengan tim sendiri (Driver, Mekanik, Kepala Pool, BM, Tim Logistik), sementara Admin IT & GA, Finance, Admin Sistem, dan Manajemen beroperasi lintas-cabang dari Head Office. Sebelumnya sistem hanya membatasi akses per-role (RBAC per-endpoint), TIDAK per-cabang — Kepala Pool cabang mana pun bisa approve Work Order cabang lain, dan dropdown armada/driver/mekanik/gudang menampilkan seluruh cabang. Ditutup lewat:
- `App\Models\User::isBranchScoped()`/`canAccessBranch(?int $branchId)` — helper terpusat; role Head Office (`GLOBAL_ROLES` const: admin_it_ga, finance, admin_sistem, manajemen) selalu lintas-cabang, role lain dibatasi ke `branch_id` miliknya sendiri.
- `FleetController`, `DriverController`, `MechanicController`, `WarehouseController`: `index()` otomatis difilter ke cabang user (mengabaikan `?branch_id=` dari role bercabang), `store()` memaksa `branch_id` ke cabang user (mengabaikan apa pun yang dikirim form), `update()`/`destroy()` menolak (403) kalau record bukan milik cabangnya.
- `RequestController::index()/show()`, `WorkOrderController::index()/show()/store()/updateStatus()/storeItem()/storeAttachment()`, `ApprovalController::pending()`: difilter/digembok berdasarkan cabang armada terkait (fallback ke cabang pengaju kalau pengajuan tanpa armada spesifik, mis. restock gudang).
- `ApprovalWorkflowService::approve()/reject()` — pengecekan branch ditambahkan SETELAH pengecekan role (jadi tetap 403 "role tidak berwenang" dulu kalau role juga salah, baru "cabang tidak cocok" kalau role benar tapi cabang beda). Finance (role global) otomatis lolos di semua cabang karena `canAccessBranch()`.
- Vendor, Cost Type, Job Type sengaja TIDAK ikut dibatasi cabang — tabelnya tidak punya kolom `branch_id` sama sekali dan tidak ada relasi lain yang menurunkan cabangnya (dianggap referensi bersama lintas cabang; skema DB tetap, tidak ada migration baru).
- Frontend: field "Cabang" pada dialog Tambah/Ubah di `MasterDataHub.vue` (Driver/Mekanik/Gudang) dan `FleetsList.vue`/`FleetDetail.vue` otomatis ter-default & terkunci (disabled) ke cabang milik user untuk role bercabang — backend tetap satu-satunya sumber otorisasi, ini murni supaya UI tidak menyesatkan. Pinia store (`stores/auth.js`) dapat `branchId`/`isBranchScoped` baru, diisi dari field `branch` pada payload login (`DevAuthController::login()`, sebelumnya tidak pernah mengirim info cabang user ke frontend sama sekali).
- `DatabaseSeeder` diperbarui: 7 cabang riil + 1 user per role bercabang per cabang (35 user) + 4 user role Head Office = 39 user seed.

Audit susulan ("apa lagi yang kurang") menemukan bahwa scoping di atas ternyata belum menyentuh beberapa endpoint terkait armada — ditutup di putaran kedua:
- `FleetController::show()` — sebelumnya bisa diakses siapa saja yang tahu ID-nya (`/fleets/{id}`, dipakai `FleetDetail.vue`) tanpa cek cabang sama sekali. Sekarang 403 kalau bukan cabang sendiri.
- `FleetHistoryController` (riwayat servis, legalitas, fuel log, biaya operasional, profitabilitas per armada — semua endpoint di `routes/modules/fleet.php`) — ditambah `guardBranch()` di kedelapan method-nya; sebelumnya tidak ada cek cabang sama sekali walau `fleet.view`/`fleet.manage` dipegang role bercabang (Kepala Pool, BM, Tim Logistik).
- `FleetProfitabilityReportController` — parameter `?branch_id=` sebelumnya bisa dipakai bebas oleh siapa pun; sekarang dipaksa ke cabang sendiri untuk role bercabang (mis. Tim Logistik hanya melihat laporan profitabilitas cabangnya, walau permission `report.view` dipegang bersama Finance/Manajemen yang tetap lintas-cabang). Filter dropdown "Cabang" di `FleetProfitabilityReport.vue` disembunyikan untuk role bercabang, karena hasilnya sudah otomatis ter-scope.
- `SparepartController` — kasus khusus: tabel `spareparts` tidak punya `branch_id`, tapi `warehouse_id` sudah pasti berada di satu cabang tertentu (`warehouses.branch_id`). Cabang sparepart diturunkan dari situ (pola sama seperti pengajuan diturunkan dari armadanya) — `index()` difilter, `store()`/`update()` menolak (403) kalau `warehouse_id` yang dikirim bukan gudang cabang sendiri (tidak dipaksa otomatis seperti Driver/Mekanik/Armada, karena satu cabang bisa punya lebih dari satu gudang sehingga tidak ada default yang jelas).

Diuji ulang dengan pola yang sama (curl, Kepala Pool Jakarta vs Samarinda): buka Detail Armada cabang lain → 403; buka tab Legalitas armada cabang lain → 403; Laporan Profitabilitas Tim Logistik tanpa filter apa pun → otomatis cuma cabang sendiri; Tim Logistik cabang lain coba tambah sparepart ke gudang Jakarta → 403; daftar sparepart Tim Logistik cabang tanpa gudang/stok → kosong (bukan error).

Satu celah kecil terakhir juga ditutup: `WorkOrderController::store()` (menetapkan pelaksana) sebelumnya tidak mengecek apakah mekanik yang dipilih berasal dari cabang yang sama dengan Work Order-nya — di UI aman karena dropdown mekanik sudah ter-scope, tapi lewat API mentah masih bisa dipaksa menetapkan mekanik cabang lain. Ditambahkan validasi: `mechanic_id` harus milik cabang yang sama dengan `branch_id` armada Work Order (ditolak 422 kalau tidak). Vendor eksternal sengaja tidak ikut divalidasi (tidak punya `branch_id`, tetap dianggap bisa melayani cabang mana pun). Diuji: assign mekanik cabang lain → 422 dengan pesan jelas; assign mekanik cabang sendiri → berhasil.

Diuji end-to-end (curl + Playwright, skenario Kepala Pool Jakarta vs Kepala Pool Samarinda): dropdown armada Driver Samarinda hanya menampilkan armada Samarinda; antrian approval Kepala Pool Jakarta kosong untuk Work Order Samarinda; approve langsung via API oleh Kepala Pool Jakarta pada WO Samarinda → 403; Kepala Pool Samarinda approve WO yang sama → berhasil; Tim Logistik Samarinda membuat driver dengan `branch_id` Jakarta di payload → tetap tersimpan sebagai Samarinda (dipaksa server); Tim Logistik Jakarta mengubah driver milik Samarinda → 403; field Cabang di dialog Tambah Armada/Driver terbukti terkunci ke "Samarinda" di UI.

**Tema warna diganti ke nuansa biru muda** (mengikuti SYOP) di `plugins/vuetify.js` — custom theme `primary`/`secondary`/`background` biru muda untuk mode terang & gelap, plus sidebar (`DefaultLayout.vue`) diberi `color="primary"` supaya menu aktif tersorot biru (sebelumnya abu-abu default Vuetify).

**Footer, multi-bahasa (Indonesia/English), dan nomor baris tabel ditambahkan.** Frontend kini memakai `vue-i18n` (`plugins/i18n.js`, kamus di `locales/id.js`/`locales/en.js`, dipilih via `stores/auth.js`-independen — persist ke `localStorage` key `tms-locale`, default Indonesia). Hampir seluruh teks UI (sidebar, tombol, label form, header tabel, pesan error, status/enum) sudah diterjemahkan lewat `t()` — termasuk label status dinamis (`StatusChip.vue`/`utils/status.js` sekarang membaca dari `enums.status.*` lewat `i18n.global.t()`, dipakai di luar komponen). `AppFooter.vue` (baru) menampilkan copyright "© {tahun} proenergi.com" + hak cipta terjemahan, dipasang dengan prop `app` pada `v-footer` supaya benar-benar menempel ke bawah viewport (bukan sekadar setelah konten) — dipasang di `DefaultLayout.vue`, `FieldLayout.vue`, dan `login.vue`. Pemilih bahasa (`LanguageSwitcher.vue`, baru) sengaja diletakkan di **top bar** (bukan di footer) sesuai permintaan eksplisit — versi ringkas (toggle ID/EN satu tombol) dipakai di `FieldLayout.vue` karena topbar aplikasi lapangan sudah padat di layar HP sempit. Semua tabel data (Master Data, Armada, Pengajuan, Antrian Approval, Aturan Approval, Asset Registry, Notifikasi, Audit Log, Laporan Profitabilitas, Rincian Biaya Work Order) kini punya kolom "No." berisi nomor urut baris — untuk `v-data-table-server` (server-paginated) dihitung `(page-1)*itemsPerPage+index+1` supaya lanjut menomori lintas halaman, untuk tabel `v-for` biasa cukup `index+1`.

**Audit fungsional menyeluruh ("apalagi yang kurang") menemukan 4 gap nyata** (ditemukan lewat pembacaan kode langsung, bukan dugaan): (1) stok sparepart tidak pernah berkurang otomatis saat dipakai di Work Order — melanggar FR-13/FR-14 secara langsung; (2) tabel `fleet_revenues` tidak punya jalur input sama sekali sehingga "Total Pendapatan" di Laporan Profitabilitas selalu Rp 0; (3) `SyopNativeAdapter::getDataPerjalanan()` belum diimplementasikan dan `getRealisasiPO()`/`getPendapatan()` masih stub (skema `proenergi` belum punya kolom penghubung PO↔armada — perlu konfirmasi tim SYOP, di luar kendali TMS); (4) belum ada automated test sama sekali (backend skeleton default, frontend tanpa test runner). User memilih memprioritaskan #1 dan #2 untuk ditutup sekarang:

- **Stok sparepart otomatis berkurang** — `WorkOrderController::storeItem()` sekarang mengurangi `spareparts.stock_qty` dalam transaksi DB dengan `lockForUpdate()` (mencegah race condition dua item WO paralel untuk sparepart sama) setiap kali item Work Order menyertakan `sparepart_id`. Kalau stok tidak cukup, ditolak (422) dengan pesan jelas menyebutkan nama sparepart & sisa stok — tidak membiarkan stok minus. Frontend: dialog "Tambah Item Biaya" di `WorkOrderDetail.vue` sekarang punya pilihan Sparepart (opsional, menampilkan sisa stok per item), otomatis mengisi Deskripsi dari nama sparepart yang dipilih.
- **Input manual Pendapatan Armada** — tab baru "Pendapatan" di `FleetDetail.vue` (endpoint `GET/POST /fleets/{fleet}/revenues`, permission `fleet.manage` untuk input — sama seperti legal-doc & fuel-log, jadi Tim Logistik & Admin Sistem) sebagai jalan pintas sementara sampai sinkronisasi SYOP beres. Form: Periode (YYYY-MM), No. PO (opsional), Jumlah — ditolak (422) kalau kombinasi cabang+periode+No. PO sudah pernah dicatat (mencegah duplikat tak sengaja). Laporan Profitabilitas (`FleetHistoryController::profitability()`, sudah ada sejak awal) otomatis membaca dari data ini tanpa perlu diubah — diverifikasi end-to-end: input Rp 5.000.000 untuk satu armada langsung muncul di tab Profit-Loss & grafiknya.
- Item #3 (integrasi SYOP) dan #4 (automated test) dicatat sebagai gap yang diketahui, belum dikerjakan atas permintaan user eksplisit — lihat bagian di bawah.

**Field master data unit logistik (armada) dilengkapi** — sebelumnya tabel `fleets` hanya punya plate_number/fleet_type/brand/model/year/capacity/branch_id/status. Ditambahkan lewat migration baru: No. Rangka/Chasis, No. Mesin/Engine, No. Keur (Uji Kir), Kepemilikan (Milik Sendiri/Sewa/Leasing), Status Leasing (relevan bila Kepemilikan=Leasing), Nomor Izin B3-Dishub, dan Status Mutasi (Tidak Ada/Pindah/Jual/Ganti Nopol). Semua field baru nullable/punya default (tidak mengganggu data lama). Frontend: dialog Tambah/Ubah Armada (`FleetsList.vue`/`FleetDetail.vue`) diperluas dengan field-field ini, field Status Leasing hanya muncul kondisional saat Kepemilikan=Leasing; `FleetDetail.vue` juga dapat kartu baru "Informasi Kendaraan" di atas tab-tab yang sudah ada, menampilkan semua field ini dalam mode lihat (sebelumnya field-field non-header cuma bisa dilihat lewat dialog edit, tidak ada tampilan ringkas). Diuji end-to-end: create armada dengan seluruh field lewat API → tersimpan benar → tampil benar di kartu Informasi Kendaraan dan terisi otomatis saat dialog Ubah Armada dibuka kembali.

**Bug ditemukan & diperbaiki: dropdown "Jenis Pengajuan" rusak, Driver/Mekanik tidak bisa membuat pengajuan sama sekali.** Root cause: pola `t('enums.requestType', {}, { returnObjects: true })` yang dipakai untuk mengubah objek locale (`{perbaikan: 'Perbaikan', ...}`) menjadi daftar opsi dropdown — pola ini **tidak berfungsi** di Composition API vue-i18n (`t()` selalu mengembalikan string, `returnObjects` cuma berlaku pada Legacy API `$t()`). Akibatnya `t(...)` mengembalikan literal string kunci ("enums.requestType") apa adanya, lalu `Object.entries()` pada string itu memecahnya jadi array karakter satu-satu ("e","n","u","m",...) — dropdown Jenis Pengajuan jadi berisi huruf-huruf acak, tidak ada opsi valid yang bisa dipilih, sehingga `form.type` tidak pernah terisi nilai valid dan submit selalu ditolak backend (422 "The selected type is invalid"). Ditemukan di `pages/field/FieldNewRequest.vue` dan `pages/requests/RequestsList.vue` (keduanya menu Jenis Pengajuan & filter Status). Diperbaiki: ganti ke `tm('enums.requestType')` (fungsi `tm()` dari `useI18n()`, dirancang khusus untuk mengambil objek/array mentah dari locale, bukan `t()` dengan opsi apa pun). Sekalian diperbaiki: label field Jenis Pengajuan di dua form itu sempat ikut memendek jadi "Jenis" saat konversi i18n sebelumnya (seharusnya "Jenis Pengajuan", beda dari header kolom tabel/filter yang memang seharusnya pendek) — ditambahkan key `requests.typeLabel` terpisah dari `requests.type`. Diuji ulang end-to-end sebagai Driver, Mekanik, dan lewat form admin: dropdown menampilkan 5 opsi jenis dengan benar, pengajuan berhasil terkirim tanpa error di ketiganya.
